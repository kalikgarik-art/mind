Документация · архитектура

Как устроен сайт Mind

Статический фронтенд

index.html и profile.html: Tailwind CDN + чистый JS. Сборка не нужна — папка deploy/ публикуется как есть.

Supabase Auth

Email и пароль проверяет сервер Supabase. Браузер получает JWT-сессию; пароли не хранятся в таблицах сайта.

Postgres + RLS

Таблицы profiles и keys защищены политиками. Активация ключа — атомарная функция activate_license_key().

Шаг 1 · Custom SMTP (Resend)

Убираем ошибку «email rate limit exceeded»

  1. Зарегистрируйтесь на resend.com → раздел API Keys → создайте ключ (начинается с re_).
  2. В Supabase откройте Project Settings → Authentication → SMTP Settings.
  3. Включите SMTP и заполните поля:
Host:     smtp.resend.com
Port:     465
Username: resend
Password: <API-ключ Resend, начинается с re_>
Sender:   no-reply@ваш-домен.ru  (или адрес onboarding Resend)

Нажмите Save. После этого письма уходят через Resend и лимиты встроенной почты Supabase больше не срабатывают.

Шаг 2 · 6-значные коды в письмах

Замена ссылки на код в шаблонах

Сайт ждет 6-значный код (экран OTP), а не переход по ссылке. Откройте Authentication → Emails → Templates и отредактируйте два шаблона:

Confirm signup

Ваш код подтверждения: {{ .Token }}

Код действует 24 часа. Если это были не вы —
проигнорируйте письмо.

Вместо {{ .ConfirmationURL }} используется {{ .Token }}.

Reset Password

Код для сброса пароля: {{ .Token }}

Введите его на сайте в форме восстановления.

Для работы OTP-ввода включите подтверждение: Authentication → Providers → Email → Confirm email = ON. Если хотите мгновенный вход без кода — выключите эту настройку, сайт покажет письмо-подсказку.

Шаг 3 · Публикация на бесплатный хостинг

Cloudflare Pages / Vercel / Netlify

  1. Загрузите содержимое папки deploy/ в репозиторий GitHub (index.html и profile.html — в корне).
  2. Подключите репозиторий: Cloudflare Pages → Create → Pages → Connect to Git; Vercel → Add New → Project; Netlify → Add new site → Import from Git.
  3. Build command: (пусто), Output directory: . (статический сайт без сборки).
  4. Получите адрес сайта, например https://mind.pages.dev.
  5. В Supabase: Authentication → URL Configuration → заполните:
Site URL:      https://ваш-домен.ru
Redirect URLs: https://ваш-домен.ru/**
               https://ваш-домен.ru/profile.html
               http://localhost:8080/**   (локальная разработка)

Синхронизируйте дату и время с шаблонов писем: без правильных URL ссылки и редиректы работать не будут.

Шаг · Подключение Discord

Привязка аккаунта Discord (OAuth)

  1. Откройте discord.com/developers/applications → New Application → вкладка OAuth2.
  2. Скопируйте Client ID и Client Secret.
  3. В Redirects добавьте: https://PROJECT.supabase.co/auth/v1/callback.
  4. В Supabase: Authentication → Providers → Discord → включить → вставить Client ID и Secret → Save.
  5. В Site URL / Redirect URLs добавьте адрес сайта: https://ваш-домен/**.
  6. В профиле нажмите Привязать Discord → произойдёт OAuth-редирект → после возврата на страницу профиль синхронизируется автоматически (RPC sync_discord() читает auth.identities).

Данные хранятся в колонках discord_id / discord_username / discord_avatar. Отвязка сначала вызывает auth.unlinkIdentity(), затем sync_discord() очищает поля.

Шаг 4 · Автовыдача ключей

Архитектура оплаты и генерации MIND-ключей

plans

Тарифы: id, title, duration_days, price_usd. Сейчас живут в assets/plansConfig.js — структура один в один повторяет будущую таблицу Supabase.

payment_methods

Способы оплаты: id, title, provider, enabled. Сейчас assets/paymentMethods.js (cards_ru, cards_global, crypto).

license_keys → таблица keys

key_code, duration_days, is_used, used_by, used_at, created_by. Генерируется в формате MIND-XXXX-XXXX-XXXX.

Схема работы: клиент вызывает handleCheckout({ planId, paymentMethodId }) → запрос уходит в CHECKOUT_ENDPOINT (Supabase Edge Function) → функция создаёт платёж у провайдера (ЮKassa / Stripe / крипто) → после успешной оплаты провайдер шлёт webhook в Edge Function → функция генерирует ключ (crypto.getRandomValues), делает INSERT в keys и обновляет profiles (service_role) → клиенту возвращается { key } и показывается окно с ключом.

POST CHECKOUT_ENDPOINT
{
  "planId": "month",
  "durationDays": 30,
  "priceUSD": 5.99,
  "paymentMethodId": "cards_ru",
  "paymentProvider": "yookassa",
  "email": "user@example.com",
  "userId": "uuid"
}
→ 200 { "key": "MIND-A7K2-XQ9P-LM4D" }

Пока эндпоинт не подключён, вы (разработчик) можете выдать себе тестовый ключ прямо на сайте — работает защищённая RPC-функция issue_license_key(email, key, days). Обычным пользователям в этом режиме показывается честное сообщение «provider not connected», без имитации покупки.

Чек-лист безопасности

  • • В config.js — только публичный anon/publishable key. Никогда не публикуйте service_role или пароль БД.
  • • Видимость панели в интерфейсе — только удобство; настоящая авторизация делается в RLS по JWT-Email.
  • • Пользователь не может менять role, license_key и expires_at — права на колонки отозваны (обновляется только hwid).
  • • Активация ключа идёт через SELECT ... FOR UPDATE — один ключ нельзя получить дважды.
  • • Регулярно обновляйте шаблоны писем и логин-URL после каждого нового домена.
